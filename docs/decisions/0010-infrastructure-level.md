# ADR 0010 — Niveau Infrastructure (MVP7) : faits extraits des fichiers de déploiement, part déclarée étiquetée, jamais une valeur de secret

**Statut :** Accepté

## Contexte
Les niveaux Architecture / Fichiers / Logique (MVP6) décrivent le code. Ils ne disent rien de la façon dont le système est **déployé et exposé** : reverse proxy, CDN, hébergement, conteneurs, et surtout ce qui **diffère entre environnements** (dev, staging, prod) — précisément là où une revue humaine est obligatoire (gouvernance §6 : configuration de production et d'infrastructure = HIGH). Le besoin exprimé : un niveau au-dessus de l'Architecture, avec les mêmes garanties que le reste de VisionLayer (faits déterministes, source de chaque fait visible, lecture sur place).

Trois questions ont été tranchées avant de coder :
1. **Quelles sources ?** Toutes celles qu'un repository RYPHA peut contenir, dès la première version : Docker Compose (base + surcharges), Dockerfile, reverse proxies (nginx, Caddy, Traefik via labels et config statique), variables d'environnement (`.env*`), workflows GitHub Actions, Terraform, manifestes Kubernetes, `vercel.json`, `netlify.toml`.
2. **Comment dire ce qu'aucun fichier ne dit** (un CDN devant le domaine, un fournisseur SaaS joint par SMTP) ? Par un fichier déclaré à la main, `.vision/infra.yaml`.
3. **Sur quel corpus valider ?** Le `reference-project` existant, étendu avec une infrastructure réaliste, plus des fixtures golden par format.

## Décision
- **Un extracteur par format** ([vision/infra/extractors/](../../vision/infra/extractors/)), chacun ne lisant qu'un fichier et produisant composants, liens et noms de variables. La découverte ([discover.ts](../../vision/infra/discover.ts)) reconnaît un fichier par son nom, puis par son contenu pour les YAML ambigus (`apiVersion` + `kind` = Kubernetes). Une erreur de parsing est notée sur la source et n'arrête jamais les autres.
- **Fusion déterministe** ([build.ts](../../vision/infra/build.ts)) : les fichiers de base sont lus avant les surcharges (`docker-compose.prod.yml`, `overlays/prod/`, `.env.production`), un même composant décrit plusieurs fois devient un seul composant dont les attributs qui varient sont rangés par environnement (`perEnv`). Un service redéfini sans `image` dans une surcharge garde le rôle appris dans la base. Les cibles de routes (`proxy_pass http://api`) sont résolues **par nom** vers les composants existants ; un nom de domaine inconnu devient un point d'entrée externe ; un nom nu inconnu devient un point d'attention, jamais un composant inventé.
- **Environnements** : déduits des noms de fichiers et de dossiers, des `environment:` des jobs CI, des contextes Netlify et du fichier déclaré, normalisés (`production` → `prod`). `all` désigne ce qui vaut partout.
- **Part déclarée** : `.vision/infra.yaml`, validé par un schéma ([declared.ts](../../vision/infra/declared.ts)). Chaque fait qui en sort porte `source.kind === "declared"` et l'interface l'affiche avec l'étiquette « déclaré » (bordure pointillée dans le graphe, badge dans le panneau, mention dans chaque lien). C'est le **seul fichier de `.vision/` écrit à la main** : il doit être versionné, contrairement aux fichiers générés — `.gitignore` passe de `.vision/` à `**/.vision/*` + `!**/.vision/infra.yaml`.
- **Secrets — règle absolue** : les variables sont extraites **par nom uniquement**. `/api/infra-file` masque toute valeur d'un fichier `.env*` (`<valeur masquée>`) et, dans les autres fichiers affichés, toute valeur dont la clé ressemble à un secret (PASSWORD, SECRET, TOKEN, KEY, DSN…) ainsi que les identifiants dans une URL. Testé : aucune valeur de `.env` ne peut apparaître dans `infra.json` ([tests/infra.test.ts](../../tests/infra.test.ts)).
- **Persistance** : `.vision/infra.json`, écrit par `scan`/`update` ([vision/model/scan.ts](../../vision/model/scan.ts)) — même cycle de vie que `model.json`. `vision infra [chemin]` l'imprime en texte ([cli/infra.ts](../../cli/infra.ts)) ; `/api/infra` le sert (calculé une fois s'il manque, pour un modèle antérieur à MVP7).
- **Interface** : niveau « Infrastructure » en tête de la barre de niveaux. Carte des composants **groupés par origine du fait** (Docker Compose, Terraform, Kubernetes, CI, Plateforme, Déclaré), filtre par environnement (un composant dont les attributs diffèrent dans l'env choisi est marqué « ≠ base »), panneau de détail (attributs, variations, liens, variables, source), configuration lue **sur place** avec la ligne du composant surlignée, et tableau « Différences » (attributs qui varient, composants propres à un environnement, variables partielles). Les libellés d'arêtes n'apparaissent que sur le composant sélectionné.
- **Mise en page** : la disposition hiérarchique d'ELK (ADR 0008) étale les groupes sans lien entre eux en une seule rangée et rend le texte illisible. Le niveau Infrastructure utilise une mise en page en deux temps ([layout.ts — layoutGrouped](../../ui/src/graph/layout.ts)) : chaque groupe est disposé seul (ELK, couches vers le bas, compact), puis les groupes sont rangés en lignes par rang de dépendance, alignés sous leur source, avec une largeur de rangée qui vise le rapport d'aspect du canevas ; les liens entre groupes sont tracés en orthogonal simple.

## Rationale
- Un extracteur par format, sans dépendance nouvelle (parseurs nginx, HCL et TOML minimaux écrits à la main, `yaml` et `zod` déjà présents) : le périmètre de chaque parseur est petit et testable par golden ; on préfère « moins mais sûr » à une dépendance lourde par format.
- La distinction extrait / déclaré est portée par le modèle (`source.kind`), pas par une convention d'affichage — un consommateur futur (contexte agent, rapport) ne pourra pas la perdre.
- Masquer côté serveur (pas côté interface) garantit que la règle tient quel que soit le client.
- Grouper par origine du fait plutôt que par « couche » (réseau, calcul, données) : la couche serait une interprétation ; l'origine est un fait vérifiable en un clic.

## Conséquences
- Nouveaux fichiers dans `examples/reference-project` (Dockerfile, compose base + prod, nginx dev + prod, `.env.example` + `.env.production.example`, workflow de déploiement, Terraform, `.vision/infra.yaml`) et fixtures golden `tests/infra-fixtures/` (Kubernetes, Caddy + Traefik, Vercel, Netlify, déclaré invalide).
- Classification du changement : **HIGH** — il modifie `policies/high-risk-paths.yaml` et ajoute des fichiers `.env*` (exemples, sans valeur réelle) et `**/infra/**` au corpus. Approbation humaine explicite requise avant merge.
- Limites connues, à traiter par ADR si le besoin apparaît : pas de résolution des `include`/`extends` compose ni des modules Terraform distants ; Kustomize lu fichier par fichier (les patches sont fusionnés par nom de ressource, pas par la sémantique Kustomize) ; Helm non lu ; pas de diff Infrastructure entre snapshots (le Diff reste au niveau Fichiers).

> **Complété ensuite** (premier passage sur un projet réel) : extracteurs Firebase (`firebase.json` + `.firebaserc`), Cloud Build, scripts de déploiement de `package.json`, services Cloud Run nommés par une commande ou une réécriture ; fichiers découverts via git (`.gitignore` respecté, liens symboliques jamais suivis) ; Dockerfile multi-lignes ; `infra.previous.json` archivé par `update`.
