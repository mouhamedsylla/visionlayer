# ADR 0011 — Niveau Technologies (inventaire prouvé, logos réels) et ce que le premier passage sur Nafar a corrigé

**Statut :** Accepté

## Contexte
Premier passage de VisionLayer sur Nafar (`learn-app`), le jalon repoussé depuis MVP5. Deux besoins exprimés en le lançant :
1. **Garder une vision globale** d'un système qui grossit — architecture, fonctionnement technique, et **toutes les technologies utilisées à un moment donné**.
2. **Voir** ces technologies : de vrais logos dans l'interface, pas des libellés.

Et le passage lui-même a cassé VisionLayer à plusieurs endroits, ce qui était le but.

## Ce que Nafar a cassé, et la correction retenue
| Constat sur Nafar | Correction |
|---|---|
| `vision scan` plante : `ressources/ressources → .`, lien symbolique en boucle (ELOOP). | Un seul listage des fichiers du projet ([scanner/files.ts](../../vision/scanner/files.ts)) : dans un repository git, `git ls-files -co --exclude-standard` — ce que `.gitignore` exclut n'appartient pas au projet ; hors git, parcours du disque. **Aucun lien symbolique n'est suivi.** Fin de la « simplification connue du MVP0 » (`.gitignore` ignoré). Nafar passe de 589 à 369 fichiers source : ceux qui disparaissent sont ceux que git ignore (dossiers de travail comme `ressources/`). |
| 9 fichiers écartés pour « erreur de syntaxe » sur une syntaxe que TypeScript accepte. | La grammaire tree-sitter refuse un `&` nu dans du texte ou un attribut JSX (`Crédits & sources`, `title="Crédits IA &"`). Ce caractère ne porte aucun fait : il est remplacé par une espace, octet pour octet (positions exactes), et le fichier est ré-analysé ; accepté **seulement** si l'arbre devient entièrement valide ([parser.ts](../../vision/parsers/parser.ts)). Seule dérogation à ADR 0004. Reste 1 fichier, pour une vraie limite de la grammaire (`x as import('…').T[]`) — signalé, pas contourné. |
| Le niveau Infrastructure ne voit que 3 composants : Firebase et Google Cloud ne sont pas lus. | Nouveaux extracteurs : `firebase.json` + `.firebaserc` (Hosting par cible, Cloud Functions, Firestore, Storage ; projet et site **par environnement** d'après les alias ; `functions/.env.<id de projet>` rattaché à son environnement et à la fonction), `cloudbuild*.yaml`, et les **scripts de déploiement** de `package.json` (`firebase deploy --project prod`, `gcloud run deploy …`) — un déploiement lancé à la main depuis un poste est un fait d'infrastructure. Un service Cloud Run nommé par une commande ou une réécriture Firebase devient un composant. Nafar : 12 composants au lieu de 3. |
| `ENV A=1 \` sur plusieurs lignes : seule la première variable du Dockerfile est vue. | Instructions Dockerfile jointes sur les `\` avant lecture. |
| `ci.yml` rangé dans un environnement « test ». | Le nom d'un workflow CI (ou d'un Dockerfile, d'un `cloudbuild.yaml`) ne porte pas d'environnement ; seuls les `environment:` des jobs le disent. |

Premier fait utile révélé sur Nafar : **12 variables des Cloud Functions** (`RENDER_URL`, `TASKS_QUEUE`, `VIDEO_DAILY_CAP`…) ne sont définies que pour le projet dev, pas pour prod.

## Décision — le niveau Technologies
- **Un inventaire, pas une déduction.** `.vision/stack.json`, écrit par `scan`/`update` ([stack/build.ts](../../vision/stack/build.ts)). Une technologie n'existe que par ses **preuves**, chacune vérifiable dans un fichier : paquet déclaré dans un manifeste (npm, PyPI, Go, Cargo, Composer, RubyGems — avec la version installée si `node_modules` est là), fichier de configuration, image de conteneur, paquet système installé dans un Dockerfile (`apt-get`, `apk`, `pip install` avec ses extras), version d'exécution (`engines`, `packageManager`, `requires-python`, `actions/setup-node`), composant d'infrastructure, fichiers d'un langage. Plus les **fichiers qui l'importent** (lien direct vers le niveau Fichiers).
- **Le catalogue nomme et range, il ne devine pas** ([stack/catalog.ts](../../vision/stack/catalog.ts)) : « le paquet `react-dom` est React », « `firebase/auth` est le produit Authentication de Firebase ». Un paquet absent du catalogue reste listé sous son propre nom (« Autres bibliothèques ») — rien n'est caché. Les sous-parties utilisées (Firebase : Hosting, Firestore, Authentication, App Check…) sont des **facettes** prouvées par un import, un paquet ou un composant.
- **Points d'attention, jamais des verdicts** : versions majeures divergentes d'un même paquet entre manifestes (`@google/genai` ^1 dans l'app, ^2 dans `functions` ; `firebase-functions` ^7 / ^6), paquet déclaré qu'aucun fichier scanné n'importe (seulement pour les bibliothèques qu'on importe, pas les outils de build/test), import d'un paquet déclaré nulle part. Une borne de pair (`>=18`) n'est pas une version et ne crée pas de divergence ; un paquet Python n'est jamais dit « jamais importé » (imports Python non analysés).
- **« À un moment donné »** : `vision update` archive aussi `stack.json` → `stack.previous.json` (et `infra.json` → `infra.previous.json`, même instant). L'écran et `vision stack` montrent ce qui est apparu, disparu ou a changé de version depuis la mise à jour précédente.
- **Logos réels** : [Simple Icons](https://simpleicons.org) (licence CC0), paquet npm `simple-icons` côté serveur. `/api/icons?slugs=…` ne renvoie que les logos affichés, groupés en une requête — jamais depuis un CDN, jamais les 3 400 logos dans le bundle. Une marque absente de Simple Icons (Azure, AWS, OpenAI…) reçoit un **monogramme**, pas un logo approximatif. Chaque slug du catalogue est vérifié par test. Les logos apparaissent : sur les cartes du niveau Technologies, sur les nœuds et groupes Infrastructure (d'après l'image, la commande de déploiement ou le format du fichier source — [stack/infraTech.ts](../../vision/stack/infraTech.ts)), sur les nœuds Architecture (technologies importées par les fichiers du module, les plus utilisées d'abord), et en marge des lignes d'un manifeste lu sur place.
- **Interface** : niveau « Technologies » en tête de la barre de niveaux. Résumé (technologies, espaces de travail, part de chaque langage), points d'attention, changements depuis la mise à jour précédente, filtre (texte, espace de travail, outils de dev), cartes par catégorie, panneau de preuves ; un clic sur une preuve ouvre le manifeste **sur place** avec la ligne surlignée (`/api/stack-file`, borné aux fichiers cités par l'inventaire, jamais un `.env`, valeurs d'allure secrète masquées) ; un clic sur un importeur va au niveau Fichiers, sur un composant au niveau Infrastructure.
- **Lisibilité** (règle déjà posée en MVP6) : un chemin dans un nœud se replie entre ses segments (`/`, `.`, `·`), jamais au milieu d'un mot ; les nœuds Architecture passent à 232 px pour que « 171 fichiers · 1405 symboles » tienne ; la rangée de logos a sa propre ligne plutôt que de tronquer le sous-titre.

## Rationale
- Le besoin est « ne plus perdre la main » : l'inventaire doit être **exhaustif** (d'où « Autres bibliothèques ») et **vérifiable** (d'où les preuves cliquables). Une liste de technologies sans preuve serait une interprétation de plus.
- Les logos d'une marque servent à la reconnaître d'un coup d'œil — un logo approximatif ou dessiné à la main tromperait ; d'où Simple Icons, et le monogramme quand la marque n'y est pas.
- Respecter `.gitignore` est aussi une règle de gouvernance : les dossiers ignorés (clés locales `.secrets/`, ressources de travail) ne doivent pas entrer dans un modèle partagé.

## Conséquences
- Nouvelle dépendance d'exécution : `simple-icons` (CC0). Classification du changement : **HIGH** — `policies/high-risk-paths.yaml` classe désormais aussi `firebase.json`, `.firebaserc`, `cloudbuild*.yaml` et les règles de sécurité Firebase (`firestore.rules`, `storage.rules`, `database.rules.json`) ; `.gitignore` gagne une exception pour les `.env.*` factices des fixtures.
- Fixtures : [tests/infra-fixtures/firebase-gcp](../../tests/infra-fixtures/firebase-gcp) (Firebase + Cloud Build + scripts + Cloud Run + Dockerfile multi-lignes), [tests/stack-fixtures/monorepo](../../tests/stack-fixtures/monorepo) (npm multi-espaces + Python + Dockerfile).
- Limites connues : imports Python/Go/Rust non analysés (seuls les imports JS/TS relient une technologie à des fichiers) ; lockfiles non lus (version installée seulement via `node_modules`) ; Cloud Run de Nafar invisible tant qu'aucun fichier ne le nomme — c'est le cas d'usage de `.vision/infra.yaml`.
