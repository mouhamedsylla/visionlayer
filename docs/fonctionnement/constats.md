# Les constats

Un constat signale un comportement que la carte seule ne montre pas : une route que personne n'appelle, une tâche planifiée qui tourne deux fois, une connexion qui peut attendre sans fin. Chaque constat porte ses preuves (les lignes qui le fondent) et les nœuds qu'il concerne.

Comme les packs, un détecteur décrit **un comportement**, jamais un projet. Il est défini ici avant d'être écrit, avec ce qui le déclenche, ce qui le fait taire, et un exemple de test par cas dans [tests/findings.test.ts](../../tests/findings.test.ts). Les projets de référence ne viennent qu'à la fin ; un constat qu'ils attendent et qu'aucune définition générique ne couvre n'est pas ajouté.

État : **produit**, **à faire**, **hors règles** (le comportement ne se lit pas dans la structure du code : il demande de comprendre un texte, ce qui revient à un agent).

## Où le constat est établi

- **Par l'assembleur**, quand il ne dépend que de la carte : une route sans appel, une tâche planifiée sur un déployable à plusieurs instances. L'assembleur ne connaît aucune technologie.
- **Par les règles d'un pack**, quand il dépend d'une technologie : une connexion sans délai d'après les valeurs par défaut documentées du pilote. Le pack émet la relation neutre `finding(Code, Sujet, Détail, Fichier, Ligne)`, et `finding_store(Code, Sujet, Technologie)` pour le stockage concerné ; l'assembleur écrit le message d'après le code et le détail. Quand le contexte de la règle est long, `finding_proof(Code, Sujet, Détail, Fichier, Ligne, PFichier, PLigne)` désigne les lignes qui fondent le constat, et seulement elles : la lecture, la mise à jour, les autres écritures de la colonne. Les preuves sont celles des faits qui ont servi à la règle.

## Les détecteurs

| Code | Ce qui le déclenche | Ce qui le fait taire | Où | État |
|---|---|---|---|---|
| `uncalled_entry` | une route HTTP d'un service qu'aucun code du dépôt n'appelle | le service n'a aucune route appelée depuis le dépôt (ses clients sont ailleurs : rien à comparer) ; une route appelée par un service externe (webhook signé) ; un chemin de contrôle de santé conventionnel (`/health`, `/healthz`, `/livez`, `/readyz`, `/ping`), appelé par l'infrastructure. Si des appels du dépôt n'ont pas pu être lus (chemin calculé), le message le dit | assembleur | produit |
| `scheduled_on_every_instance` | un déployable porte des tâches planifiées et tourne sur au moins deux instances : chaque tâche s'exécute autant de fois | une seule instance, ou un nombre d'instances inconnu | assembleur | produit |
| `missing_timeout` | une connexion ouverte sans aucune des options de délai du pilote, quand sa documentation dit que l'attente par défaut est sans limite (node-postgres : `connectionTimeoutMillis` vaut 0) ; ou des commandes mises en attente sans limite (ioredis : `maxRetriesPerRequest: null` sans `commandTimeout`) | une option de délai écrite ; des options passées par une variable ou étalées (`...base`), qui ne sont pas lues ; un pilote dont le délai par défaut est fini (MySQL2, MongoDB, node-redis, Postgres.js) | pack `stores` | produit |
| `personal_data_logged` | un journal (console, pino, winston) qui écrit le corps entier d'une requête HTTP, ou un champ nommé comme une donnée personnelle (`email`, `password`, `phone`…) | un journal qui masque des champs (`redact` de pino) ; un champ qui n'est qu'un morceau d'une expression plus profonde | pack `logs` ([inventaire](packs/logs.md)) | produit |
| `dead_code` | une fonction exportée (`export function f`, `export const f = () => …`, `export { f }`) qu'aucun fichier n'importe et que son propre fichier n'emploie pas, dans le code d'un déployable ou dans un fichier que personne n'importe rangé avec lui (même dossier de premier niveau, `src/`) | le fichier est lancé (par un manifeste ou un script de `package.json`), est un test, une configuration (`*.config.ts`), ou est importé en entier (`import * as m`, `require`, import dynamique, `import "./x"`) ; un fichier qui ré-exporte tout et dont le nom est employé à travers lui ; la fonction est le code d'un point d'entrée ; un fichier rangé ailleurs (un script, une maquette) | règles communes (`core`) | produit |
| `unused_value` | une valeur permise d'une colonne (`text("status", { enum })`, `pgEnum`, `mysqlEnum`) qu'aucune écriture ne donne : ni `.set`, ni `.values`, ni `.default`, ni une écriture SQL brute | une écriture de la colonne dont la valeur n'est pas écrite en clair (`.set({ status: next })`), ou de la table sans colonnes visibles (`.set(patch)`) : on ne sait pas ce qui est écrit | pack `drizzle` (formes E1 à E7) | produit |
| `unguarded_route` | une route dont le chemin, ou le préfixe d'un routeur qui la contient, a un morceau qui commence par `admin`, et qu'aucune garde de rôle ne protège. Une garde est une fonction du dépôt qui répond 403 (rôle) ou 401 (connexion), ou qui en appelle une ; le message dit si la route n'a qu'une garde de connexion, ou aucune garde lue | une garde de rôle sur la route, sur son routeur ou son préfixe avant elle, ou appelée par son code (formes G1 à G4) | pack `express` | produit |
| `write_then_enqueue` | dans une même fonction, une écriture faite dans une transaction puis un message publié après elle ; ou une écriture sur une connexion ordinaire puis une publication : si la publication échoue, l'écriture reste | la publication est dans la même transaction ; l'écriture passe par un objet reçu en paramètre (`tx` donné par l'appelant) : on ne sait pas s'il y a une transaction | règles communes, avec `tx_span` et `write_ctx` du pack de l'ORM et `publish_at` du pack de la file | produit |
| `race_read_then_write` | une fonction lit des lignes filtrées sur une colonne, puis met à jour la même table sans refiltrer sur cette colonne, alors qu'une autre fonction met à jour cette colonne | un verrou (`.for("update")`) sur la lecture, ou une mise à jour qui refiltre sur la colonne | règles communes, avec `read_filter`, `upd_at`, `upd_where`, `upd_set` du pack `drizzle` | produit |
| `order_assumption` | un code suppose l'ordre d'arrivée des événements, contre ce que dit un commentaire | — | — | hors règles : il faut comprendre le commentaire (« l'ordre n'est jamais supposé ») et le comparer au code ; c'est le travail d'un agent, dont la note viendra par le contexte |
| `doc_contradiction` | la documentation dit une valeur, le code en garde une autre | — | — | hors règles : il faut relier « libérée après 15 minutes » du README à `HOLD_MINUTES = 30` ; c'est le travail d'un agent |

Un constat est une affirmation sur le dépôt : « aucun code du dépôt n'appelle cette route » est vrai ou faux en relisant le dépôt. Il ne juge pas si c'est un défaut : une route d'administration appelée à la main peut être voulue.
